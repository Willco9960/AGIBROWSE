# Task execution runner

Run `npm run test:runner` (Node 24, no install needed). Run `node tools/runner/demo.mjs` for the active 005 Sol 6.1/medium route: preflight passes using the previously reviewed 004 foundation, launch consumes the enforced settings, missing executor receipts produce `done:false`, null provider identity/tokens/cost, and exit 2. The demo prints its append-only temporary audit path. `npm run runner:demo` also works; npm may map the expected nonzero exit to 1.

`tools/runner/routing-manifest.json` is the repository's canonical execution input: all 90 approved assignments, prerequisite sequence, original/current criteria, structured fallbacks, eight addendum entries and nine accepted two-tier contract extensions. No board identifiers/passwords are copied. Changing approval requires updating that document explicitly; title/model tags never override it. Runtime validation rejects omitted/malformed routing, criteria and prerequisites. The operator controls this local file; it is not a signed authorization service.

## CLI

1. Create an operator-owned request JSON with `taskId`, exact `config.model/reasoning/mode`, `config.availableRoutes`, `config.trustedAdapter:{path,sha256}`, `completions`, `auditPath`, and optional `completion`. SHA256 pins the reviewed adapter module bytes before import. Available routes must come from the trusted launcher capability inventory; listing a route is not provider availability proof.
2. Run `npm run runner:preflight -- request.json` to check configuration and prerequisite evidence before work. Run `npm run runner:run -- request.json` to check, launch, verify receipts and apply the completion gate. CLI imports only the pinned operator-selected adapter; do not accept adapter/config/manifest input from tasks or pages. Imported dependencies must be reviewed/pinned by the operator as part of that adapter's trust boundary.
3. Read JSON output and JSONL audit. Direct CLI exit codes: 0 = passed preflight or verified completion; 1 = blocked/error; 2 = execution recorded but completion unverified. The runner does not move board cards.

## Trusted adapter contract

A module exports default `{id,getHistory,launch,verifyReceipt,verifyCompletion}`. The library takes that adapter object directly; CLI checks its configured hash. This trust pin identifies local reviewed code, not provider authenticity. A production adapter must independently authenticate evidence (provider/launcher/reviewer records), never merely echo JSON fields or accept `trusted:true` from the caller. The included demo adapter is restricted to the previously reviewed 004 prerequisite and cannot verify any executor receipt.

`getHistory(taskId)` must return the authoritative complete task-attempt history from the trusted executor, including all retries/routes. Return an empty array only if there are no prior attempts; refuse if history cannot be established. `verifyReceipt(raw)` authenticates every historical/current record and returns its normalized fields or null. Caller-supplied history is forbidden. One failed focused repair can retry primary; after two, a declared fallback requires explicit `config.fallback:{failedAttempts:[id1,id2],failingCase,reason}`. No declared fallback means no upgrade. Three focused repair failures across routes stop the next launch for assumption review. Same-route handoffs also require the explicit record. An adapter must serialize launches per task, persist attempts before returning, and recover interrupted launches honestly; this runner does not provide a distributed lock or automatic retry.

`launch({runId,attemptId,taskId,model,reasoning,mode})` must consume these settings when configuring the real executor, block unsupported combinations, and supply its raw receipt. The runner never substitutes models. `verifyReceipt` returns `{trusted:true,source,runId,attemptId,taskId,status,launcherObserved,providerObserved,providerSource,usage,latencyMs}`. `status` is completed/failed/unknown. Observed settings are `{model,reasoning,mode}`; historical focused failures also carry `focusedRepair:true,failingCase`. Launcher settings must match the enforced route. Optional provider settings must match and have an authenticated source; otherwise the record is rejected. Provider identity stays null when only a launcher receipt exists. Historical records must carry unique attempt IDs and valid task/run/route/source provenance.

`verifyCompletion(raw)` must independently review all acceptance evidence, then return `{trusted:true,taskId,status:'verified',reviewer,source,verifiedAt,evidence,criteria,runId}` or null. Each evidence item has repository-relative `path`, byte `sha256` and `description`. Each criterion has the exact manifest `criterion`, `passed:true` and nonempty `evidence:[indices]`. The runner hashes evidence bytes, requires every criterion in order, and binds current completion to the current run. Prerequisites use their previously verified run; legacy tasks may be adopted only through the trusted reviewer's explicit review of existing evidence. For the library, `completion` may be an async callback receiving current run/attempt/task IDs; CLI receives a prearranged record validated by the adapter. Missing/partial/changed evidence never becomes Done.

## Accounting

Every attempted launch appends launch/attempt/completion records with UTC timestamps, run and attempt identity, configured and observed settings, provenance, errors, measured elapsed milliseconds and usage. Preflight blocks append a blocked record. Usage is `{input,output,cached,reasoning}` with nonnegative integer counts or null. Input includes cached tokens; output includes reasoning. Missing counts remain null. Malformed counts block completion; failed/unknown/missing receipts cannot complete. Unknown provider model always means `actualModel:null` and `cost:null`, even when the configured model is known.

Optional `config.rates` supplies `{version,source,currency,asOf,models:{MODEL:{input,output,cached}}}` rates per million tokens. Cost uses `(input-cached)*inputRate + cached*cachedRate + output*outputRate`, divided by one million; reasoning is not billed twice. Cost exists only with authenticated provider identity, all billing counts and known rates. No prices are hardcoded; test rates are synthetic. Codex account usage percentages are separate from task token usage and never appear as task cost. JSONL writes use append mode; this is a local diagnostic audit, not a tamper-resistant ledger. Preserve it externally if required by your executor.
